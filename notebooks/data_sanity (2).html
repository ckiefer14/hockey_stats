Data Sanity Checks¶

Verification that the loaded NHL data is correct, complete, and trustworthy before building models on it. Re-run this notebook after any data pull.

Sections

  1. Setup
  2. Row counts & per-season coverage
  3. Team coverage (home/away balance)
  4. Shot coordinate distributions (highest-value visual check)
  5. Goals reconcile with final scores (highest-value correctness check)
  6. NULL rates on model-critical columns
  7. Single known-game deep dive
  8. game_events completeness (new — full play-by-play)
  9. Event ordering & join-key integrity (new)
  10. shot_context coverage & flag plausibility (new — rebound/rush)
  11. Blocked-shot attribution check (new — known API quirk)
  12. Rink plot smoke test (new — viz)

The division of labor: sections 2–3 confirm the data is present and complete, 4–6 confirm it is internally consistent, and 7 confirms it matches external reality. Sections 8–11 do the same for the full-event tables that back the rebound/rush xG features: 8–9 are presence/integrity, 10–11 are consistency. Section 12 is a visual end-to-end check.

3. Team coverage (home/away balance)¶

Every team should have a roughly equal total number of games, and home games should be ~50% of each team's total. A team with a lopsided home/away split or a suspiciously low total points to a parsing or filtering problem.

4. Shot coordinate distributions (highest-value visual check)¶

The single most informative check. Load every shot with coordinates and look at where they land.

What healthy data looks like: two symmetric clusters (the NHL records shots from both ends, so raw x spans roughly -100 to +100), density concentrated in front of each net, thinning toward the blue lines, near-empty at center ice.

Red flags:

  • A spike at exactly (0, 0) -> missing coords stored as zero instead of NULL
  • Strong left/right asymmetry -> home/away coordinate-flip bug
  • Points outside +/-100 (x) or +/-42.5 (y) -> units / scaling problem

5. Goals reconcile with final scores (highest-value correctness check)¶

For a sample of games, count goal events in shot_events and compare to the official home_score / away_score in the games table. If these disagree, something is wrong with how goals are recorded or attributed -- which would poison both the xG model (mislabeled outcomes) and the game model (wrong counts).

Expected quirk: shootout-decided games. The official score includes one shootout-winner goal that does not appear as a normal goal event in play-by-play. So expect a small number of off-by-one mismatches that cluster on one-goal-margin games. That's the shootout signature, not a bug -- but this check is how you learn to recognize it.

# Count goal events per (game, team)
goal_events = pd.read_sql('''
    SELECT game_id, team_id, COUNT(*) AS goals_in_events
    FROM shot_events
    WHERE event_type = 'goal'
    GROUP BY game_id, team_id
''', conn)

# Official scores + team ids, joined from games + schedule
games = pd.read_sql('''
    SELECT g.id AS game_id, g.home_score, g.away_score,
           g.home_team_abbrev, g.away_team_abbrev,
           sc.home_team_id, sc.away_team_id
    FROM games g
    JOIN schedule sc ON sc.game_id = g.id
''', conn)

# Build quick lookup: (game_id, team_id) -> goal count
goal_lookup = {(r.game_id, r.team_id): r.goals_in_events
               for r in goal_events.itertuples()}

def event_goals(game_id, team_id):
    return goal_lookup.get((game_id, team_id), 0)

# Sample for speed (vectorize later if it looks clean)
sample = games.sample(min(300, len(games)), random_state=42).copy()
sample["event_home_goals"] = [event_goals(r.game_id, r.home_team_id) for r in sample.itertuples()]
sample["event_away_goals"] = [event_goals(r.game_id, r.away_team_id) for r in sample.itertuples()]
sample["home_match"] = sample.home_score == sample.event_home_goals
sample["away_match"] = sample.away_score == sample.event_away_goals
sample["full_match"] = sample.home_match & sample.away_match

mismatch_rate = 1 - sample.full_match.mean()
print(f"Sampled games: {len(sample)}")
print(f"Full-match rate: {sample.full_match.mean():.1%}")
print(f"Mismatch rate:   {mismatch_rate:.1%}")

6. NULL rates on model-critical columns¶

How much of the data is actually usable for the xG model. Some NULL coordinate rate is expected and legitimate -- blocked shots have no recordable shot location. You want to know the number so you can decide how to filter, and so a 40% rate (a real problem) doesn't hide behind an assumed 15% (just blocked shots).

9. Event ordering & join-key integrity (new)¶

Two structural facts the derivation depends on:

  • Join key. shot_context joins to shot_events on (game_id, event_id) — every shot row must find its match in game_events.
  • Chronology. The API's eventId is not in play order; sort_order is. game_seconds must be non-decreasing when walked in sort_order — if this fails, every rebound/rush flag is suspect.

# 9b. Chronology: game_seconds non-decreasing along sort_order (sampled games),
# and how often eventId order disagrees with sort_order (why we never sort by it).
rng = np.random.default_rng(42)
all_ids = [r[0] for r in conn.execute("SELECT DISTINCT game_id FROM game_events")]
sample_ids = rng.choice(all_ids, size=min(200, len(all_ids)), replace=False)

non_monotonic, id_order_differs = 0, 0
for gid in sample_ids:
    g = pd.read_sql('''
        SELECT event_id, sort_order, game_seconds FROM game_events
        WHERE game_id = ? ORDER BY sort_order
    ''', conn, params=(int(gid),))
    if (g.game_seconds.diff().dropna() < 0).any():
        non_monotonic += 1
    if not g.event_id.is_monotonic_increasing:
        id_order_differs += 1

print(f"Sampled games: {len(sample_ids)}")
print(f"Games where time runs backwards along sort_order: {non_monotonic}  (expect 0)")
print(f"Games where eventId order != sort_order: {id_order_differs} "
      f"({id_order_differs/len(sample_ids):.0%}) — any nonzero count is the reason "

10. shot_context coverage & flag plausibility (new — rebound/rush)¶

Coverage contract: one shot_context row per unblocked, period ≤ 4 shot in game_events. Plausibility: rebounds ~8–13% of unblocked shots (sensitive to the window: NST uses 3s, MoneyPuck 2s). Rush rates land in the mid single digits with this event-sparse definition — most shots have no recorded event within 4 seconds behind them — so validate rush against NST's per-game rush attempt counts rather than a fixed band.

The teeth of this section is the signal check: rebound and rush shots should convert to goals at a visibly higher rate than other shots — that's the entire reason they're xG features. If conversion is flat, the flags are mislabeled even if the rates look right.

11. Blocked-shot attribution check (new — known API quirk)¶

The NHL API attributes blocked-shot events to the blocking (defending) team. Confirmed in our data (zone codes ~96% 'D'), so derive_shot_context re-attributes blocks to the shooting team by default (blocked_shots_owned_by_blocker=True), flipping team and zone before the event enters the bookkeeping. This both adds true rebounds (a shooter's follow-up off their own blocked attempt) and removes false ones (the blocker "shooting again" from 180 feet away). Rush flags are provably invariant to the flip — the zone comparison is relative, so re-attribution cancels out.

This cell stays as a tripwire: if a future API change flips attribution to the shooter ('O'-dominant), set blocked_shots_owned_by_blocker=False and rebuild.

After changing attribution or windows: build_shot_context(conn, rebuild=True).
